## 1. What a mapping is here

The dictionary sheet `MAPPINGS_INTEROPERABILIDADE` lists 18 mappings, MAP-V2-001 to MAP-V2-018. Every row reads: authority "Canonical model; target is exchange representation", mapping release required "Yes", status "prepared Phase 1". So the canonical model is the authority, a FHIR, MIABIS, SensorThings, WoT, CloudEvents or GQL document is an exchange copy, and no mapping is approved.

The code says the same on every export it builds: `buildFhirExport` (`fhir.service.js`) and `buildMiabisExport` (`miabisExport.service.js`) both answer `mappingReleaseId: null` and `conformanceClaimed: false`. The export and import code names its mapping IDs in `EXPORT_MAPPINGS` (`fhir.service.js`, MAP-V2-006 to MAP-V2-009) and `MAPPINGS` (`miabisExport.service.js`, MAP-V2-010 and MAP-V2-011), each with `status: 'prepared Phase 1'`.

Three ways the code handles a round-trip limitation, named in the table below:

- **Loss record**: the import or export writes down what it did not carry. FHIR Bundle staging (`stageBundle`, `fhir-import-staging.service.js`) stores `roundTripLoss` on each staged record (`buildRecordRoundTripLoss`, `round-trip-loss.js`: unmapped paths, capped at `MAX_UNMAPPED_PATHS` = 50, plus the fixed `ROUND_TRIP_LIMITATIONS` sentences) and on the batch (`buildBundleRoundTripLoss`: the Bundle resources no record attaches). Paths only, never values. The FHIR exports return `roundTripLimitations` (`EXPORT_ROUND_TRIP_LIMITATIONS`); the import of Provenance, AuditEvent, DocumentReference and ResearchStudy stores `limitations` (`IMPORT_ROUND_TRIP_LIMITATIONS`, `import-mappings.js`); the MIABIS export returns `roundTripLoss: { droppedFieldCount, dropped }`.
- **Refusal**: the code does not write the canonical record or the value at all (a transform that leaves a value out rather than guessing it, an import that creates no record).
- **Nothing**: the transform exists, or the canonical entity exists, and no loss is recorded.

## 3. Profiles and mapping releases

- `conformance-registry.js` holds the base `profiles`, `namespaces` and `approvedAuthorities`, all empty on purpose: the requisitos populate profiles and mappings in Phase 2 (decision `2026-10-23-fhir-validator-version-profile-identifier-system.md`). The validator adds the stored rows from `/api/fhir-profiles` and `/api/identifier-namespaces`. A declared profile or identifier system no eligible row matches is refused (fail closed).
- The JSON schemas the validator checks structure against are `api/backend/src/resources/fhir/profiles/` (Bundle, Observation, Organization, Patient, Specimen). They encode R4; a resource's own `fhirVersion` other than `4.0.1` or `R4` is refused.
- InteroperabilityMappingRelease and FHIRProfileRegistry are models (decision `2026-10-22-interoperability-mapping-release-structures.md`) stored through `/api/interoperability-mapping-releases` and `/api/fhir-profiles`. Staging records, per batch and per record, the release an eligible profile row names (`createMappingReleaseResolver`, `fhir-import-staging.service.js`); a profile with no eligible row names none. No export names a release.
