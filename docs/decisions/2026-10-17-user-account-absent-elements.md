# 2026-10-17: seven UserAccount elements stay absent from the user document

Dictionary: UserAccount P1X-0182, 0183, 0188, 0191, 0192, 0196 and 0201 (Dicionário de Dados v2.0.0). Issue #1386 (the remainder of #1330).

## Question

The conformance guard recorded seven UserAccount elements as `TODO(#1330)` absences: the user document never emits them. `2026-10-11-user-account-names.md` moved the document to its canonical names and `2026-10-16-user-account-timestamps.md` settled its two timestamps, but neither said whether these seven are to be built. Each needs either a build or a recorded reason to stay absent.

## Decided

All seven stay absent, and the guard records each as a deliberate absence. No decision below is new policy: each is the repo's own inference from a choice it has already made, cited where it was made.

1. **P1X-0182 `userAccountId` (uuid, 1..1 Core): the account's id is its `_id`. No second id field is added.** Every reference to a user already stores `String(user._id)` under the canonical name `userAccountId`: the role assignments (`services/rbac-assignment.service.js:21-28`, `userAccountId: String(userAccountId)`), the sessions (`models/Session.js:30`), the recovery code sets (`models/RecoveryCodeSet.js:16`), and the access token's `userID` claim, `user._id.toString()` (`services/auth.service.js:327`, `:342` and `:799`). A separate uuid would give one account two ids, and every existing reference would still point at the old one. Recorded departure: the value is a 24-hex ObjectId string, not the dictionary's uuid. `fieldsOf` is pure and runs before insertion, so it cannot emit `_id`.
2. **P1X-0183 `actorId` (Reference(Actor), 1..1 Core): absent, because no Actor entity exists in the code.** There is no Actor model under `api/backend/src/models/`; the dictionary's Actor rows are P1X-0128..0134. Every actor the code records is the user id itself: `core/use-cases/RegisterSampleUseCase.js:159` (`actorId: command?.actor?.userId`) and `interface/routes/sample.routes.js:1789` (`actorId: req.user?.userID ...`). The account is its own actor until an Actor entity is built, so there is nothing to reference.
3. **P1X-0188 `institutionLegacy` (0..1 Extensão local): absent, because the migration it aliases is finished.** The dictionary row calls it a transitional alias of `institution`, "usar apenas durante migração". `scripts/migrateUserOrganizations.js` (header lines 1-10; the `$unset` at 99) moved `institution` to `organizationId` under #347 and removed it from the document, and `frontend/src/types/models.ts:678` records the cutover. The document carries `organizationId` (P1X-0187), which is present.
4. **P1X-0191 `accessTypeLegacy` (0..1 Extensão local): absent, because the 1-4 level is no longer stored on the user.** #427/#428 stopped persisting `accessType` and `roleName` on the user document (`interface/routes/auth.routes.js:281-288`). The level is resolved on each read from the active role's `hierarchyLevel` (`services/rbac-assignment.service.js:40-44`, `resolveUserHierarchyLevel`), and the dictionary row itself says canonical authorization uses Role and Permission. Storing it again would bring back the second source of truth that the #421 cutover removed (`rbac-assignment.service.js:5-19`).
5. **P1X-0192 `primaryRoleId` (Reference(Role), 1..1 Core): absent, because the primary role is derived from UserRoleAssignment and not stored on the user.** The primary role is the active assignment whose role is one of the four accessType-derived roles; additive roles such as `auditor` are kept apart (`rbac-assignment.service.js:318-343`, `changeUserRole`, #616). One primary role can carry several assignments, one per organization scope (#1358, same function, lines 355-368), and an assignment lapses by `validUntil` (`getActiveAssignments`, lines 21-29). A stored copy would need a write at every role change and at every expiry, and it would go stale silently between them. #426-#431 stopped reading role identity off the user document for exactly this reason.
6. **P1X-0196 `mfaMethod` (code, 0..1 Condicional): absent, because only one method exists and it is set by policy.** `governance/securitySettingCatalog.js:53` fixes `authentication.mfaMethod` to the enum `['totp']`, and the dictionary row itself notes that only TOTP is implemented. No account can have a different value, so a per-account copy would record nothing. It becomes worth building when a second method exists.
7. **P1X-0201 `mfaLockedUntil` (dateTime, 0..1 Condicional): absent, because its condition never holds.** The row applies "quando a política usar duração", and no MFA lock-duration policy exists. The MFA lock is the `mfaLocked` flag, cleared only by an administrator's reset-mfa (`services/auth.service.js:752-768`, #683). The only lockout duration in the catalog, `authentication.lockoutDurationMinutes` (`securitySettingCatalog.js:56`), is the password side's, and that side ends in `accountLockedUntil`, already recorded as a local extension. `tests/unit/auth.service.processLogin.unit.test.js:355-366` pins the flag-only contract.

Paths starting `services/`, `models/`, `core/`, `interface/`, `governance/` or `scripts/` are under `api/backend/src/`; `tests/` is under `api/backend/`.

Made by the 2026-10-17 coordinator sitting on #1386, by inference from the repo's existing choices; the owner may reverse any of the seven.
