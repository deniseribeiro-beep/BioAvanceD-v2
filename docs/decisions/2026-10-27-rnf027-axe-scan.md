# 2026-10-27: RNF027 C2's automated rule check is an axe scan with the WCAG 2.1 A and AA tags of /login and eight core administrator pages, in Chromium, with no rule disabled

Requirement RNF027 C2. Issue #1324.

## The question

RNF027 asks the interface to follow accessibility principles "compatíveis com nível AA", and C2 asks that "Campos possuem rótulos, foco visível, contraste adequado e mensagens associadas". The keyboard and focus cases in `tests/e2e/rnf027-interface.spec.ts` check some of this by hand; nothing checked labels, contrast and names by rule. Which rules, on which pages and in which browsers, prove C2's automated checks?

## Decided

`[inference]`, by the coordinator for #1324 on 2026-10-27. The `@axe-core/playwright` dev dependency was approved by Dennis on 2026-10-27.

1. **Rules: the axe tags `wcag2a`, `wcag2aa`, `wcag21a` and `wcag21aa`.** RNF027 asks for "nível AA"; WCAG 2.1 is the version whose A and AA criteria axe's tags cover. No rule is disabled, and no element is excluded or narrowed out of a scan: a violation is fixed in the component that renders it.
2. **Pages: `/login`, unauthenticated, and, as the default administrator at 1366x768, `/dashboard`, `/patients`, `/samples`, `/results`, `/facility-management`, `/reports`, `/user/security` and `/system-management`.** These are the core pages among the 19 sidebar destinations an administrator sees (`Sidebar.tsx`). `tests/e2e/rnf027-axe.spec.ts` scans each once it shows its own heading and, because most of these pages render the heading before their reads settle, once that page's own loading markers are gone (its "Carregando..."/"Loading..."/"Cargando..." text, and the dashboard's "..." KPI values), within 20 s. It never waits for network idle, since pages poll. Without that wait the scan reads the loading state and misses what the settled page renders.
3. **Browser: Chromium only.** axe reads the rendered DOM, so one engine proves the rules; the engine matrix stays the interface spec's (see `2026-10-27-rnf027-browser-and-viewport-matrix.md`).

The scans found these violations, each fixed at its cause:

- the icon-only back button on `/patients` had no accessible name (`button-name`);
- the inactive and danger MFA pills on `/user/security` drew `--danger` text on their light red tint at 3.2:1 (`color-contrast`);
- once the pages settled, three error texts were red on white or on a light red tint below 4.5:1 (`color-contrast`): the dashboard's temperature-readings error (`--danger`, 3.8:1), the `/patients` load and connection error banners (`#dc2626` on `#fee2e2`, 3.9:1) and the `/samples` table's error cell (`--danger`, 3.8:1). Each now uses `#991b1b`, 6.8:1 or more.

The active MFA pill on `/user/security` drew `--success` on its green tint at 2.9:1 and now uses `#065f46`, 6.5:1. No scan reaches it: the seeded administrator has MFA off and no recovery codes, so only the inactive and danger pills render, in mock and real mode alike.
