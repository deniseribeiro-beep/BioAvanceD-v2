# 2026-11-12: The production ingestion route keeps no transient state, proves telemetry convergence on the telemetry routes, and proves its transaction in the backend unit suite

Requirement RF029 AC4, AC5, AC6. Issue #1523.

## The question

RF029 AC4 asks that "dados transitórios" live "somente no Redis", AC5 that telemetry be deduplicated with its times and hashes kept and its MQTT, HTTPS and adapter paths converge on one canonical contract, and AC6 that the outbox event be emitted "na mesma transação MongoDB" (`docs/extracted-v2.0.0/requisitos.md` lines 943-947). The e2e suite proves `POST /api/ingestion/records` against the real stack (`tests/e2e/ingestion-records.spec.ts`). Which of these three clauses can an e2e test on that route prove, and where is each of the others proven?

## Decided

`[inference]`, from the specification and the repo's pattern, for #1523, on 2026-11-12. The pattern: a criterion is proven where the behaviour it names lives, by the instrument that can reach it, and a route that refuses a concern is not that concern's proof. `docs/decisions/2026-10-24-ingestion-telemetry-reading-refused.md` already sends TelemetryReading to the telemetry routes rather than storing it in the wrong place.

1. **RF029 AC4, Redis clause: the ingestion modules and route keep no transient state of their own, so they have none to place outside Redis.** Every write of `POST /api/ingestion/records` is a durable record: the entity document, `ingestionQuarantineRecords`, `ingestionIdempotencyKeys`, `missingDataReasons`, `dataQualityAssessments`, the outbox event and the audit row. The idempotency key is no transient either: `api/backend/src/ingestion/productionIngestion.js` `ingestUnderRelease` calls the gateway with `idempotencyKey: null`, so the route never writes a `claimed` key and records a key only `completed`, and a key does not expire (`docs/decisions/2026-10-21-telemetry-client-key-store.md` item 2). No module under `api/backend/src/ingestion/` nor `api/backend/src/interface/routes/ingestion.routes.js` requires `api/backend/src/config/redis.js` or `api/backend/src/config/queue.js`. Instrument: from the repo root, `git grep -n -I -E "require\(.*(redis|queue)" -- api/backend/src/ingestion api/backend/src/interface/routes/ingestion.routes.js` prints nothing. A later transient on this route (a lock, a rate window, a cache) goes to Redis.
   One app-wide transient does reach this route: `api/backend/app.js`'s `globalLimiter` (`express-rate-limit`, mounted with `app.use(globalLimiter)` outside tests) passes no `store:`, so it counts each client's failed requests, a 422 quarantine included, in process memory, not in Redis. It is every route's limiter, not the ingestion route's, and it is left under "Not decided here".
2. **RF029 AC5 is proven on the telemetry routes, not here.** This route refuses `TelemetryReading` 422 `INGESTION_STORE_UNSUPPORTED` (`docs/decisions/2026-10-24-ingestion-telemetry-reading-refused.md`), so it deduplicates, hashes and converges no reading. The telemetry paths share the `TelemetryReading:<sensorId>` key scope in `ingestionIdempotencyKeys` (`docs/decisions/2026-10-21-telemetry-client-key-store.md` item 1). Their proof is #1515 (clock drift and a corrupted payload's hash, beside the duplicates already proven) and #1516 (the MQTT path against the real broker, beside HTTPS).
3. **RF029 AC6's atomicity is proven by the backend unit suite, not by e2e.** An e2e test against the real stack cannot fault the outbox append between the insert and the commit. `productionIngestion.js` runs the entity insert, the outbox append, each MissingDataReason and the DataQualityAssessment inside one `withTransactionWhereSupported` (`api/backend/src/utils/mongoTransaction.js`: a transaction on a replica set or mongos, sequential writes elsewhere). Instrument: `api/backend/tests/unit/ingestion/productionIngestion.test.js` cases "2. on a replica set, the insert and the append receive the same session", "2b. on a replica set, every MissingDataReason insert receives the same session" and "3. on the session path a failing append rejects, with the insert and the append in the same session". The e2e suite proves the committed outcome: the accepted cases of `tests/e2e/ingestion-records.spec.ts` find the document with exactly one outbox event.

## Not decided here

- **An integration test that faults a real replica-set transaction.**
- **Moving the app-wide rate limiters' windows to a Redis store.** `globalLimiter`, `authLimiter` and `consentLimiter` in `api/backend/app.js` all use the default memory store. RF029 AC4's clause would ask a Redis store of them, and that is a decision for every route, not this one.
- **Redis use by any other route.**
- **TelemetryReading ingestion through this route.**
