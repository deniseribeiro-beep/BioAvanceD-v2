# 2026-10-08: a collection's governance context, its approvals, and the event that sets or converts it

Requirements: RF004 AC3-AC5 and AC7, RF020 AC2-AC4, RF021 AC2, AC3 and AC6, Requisitos v4.0.0; dictionary v2.0.0 CollectionGovernanceApproval V2E-0067..0075, BiorepositoryContext V2E-0076..0087, BiobankGovernanceContext V2E-0088..0096, CollectionGovernanceEvent V2E-0097..0104, RULE-001/002, REL-0168. Issue #1310.

## Decided

1. **The context is embedded on the Collection document as `governanceContext`.** The v2.0.0 synthetic examples (`BioAvanceD_Exemplos_Registros_Sinteticos_v2.0.0.json`, `biobankExample.collection` and `biorepositoryExample.collection`) store it there. It holds only the regime's own fields and its id (`biorepositoryContextId` or `biobankGovernanceContextId`), so RULE-001/002's "exactly one, the other absent" is a property of the stored document.
2. **Approvals are their own collection, `collectionGovernanceApprovals`,** since a collection may hold several (REL-0033, 0..*) and an event or a context names them by id.
3. **Only a CollectionGovernanceEvent writes a collection's regime or context.** `POST /api/collections/:id/governance/events` records `created` for the first context and `regime_change` for a new regime. The master-data PUT still refuses a regime change (RF020 AC4), and its update fields never included `governanceContext`.
4. **Approval status.** The dictionary's vocabulary cell for V2E-0074 reads `draft` and its example `active`; the xlsx says no more. The set is `draft`, `active`, `suspended`, `revoked`. The last two are an inference from RF021 AC6 ("aprovação ... inativa"): an approval withdrawn for a time, or for good. `revoked` is final. Expiry is not a status: an approval is in force while `active` and inside `effectivePeriod`.
5. **Other closed sets.** `newEthicsReviewRule` takes the two values the dictionary gives, `always` and `when_required_by_policy`. `applicableConsentModel` takes Consent.consentModel's four (ENUM-0043..0046). `decisionType` takes `created` and `regime_change`.
6. **RF021 AC3's "prazo ou condição de encerramento"** is met by either `plannedEndDate` or `closureCondition` (V2E-0086/0087, each conditional); a biorepository context needs one of them.
7. **Registration gate.** A specimen enters a collection only when the collection has a regime, the context that regime names, a biorepository context inside its validity, and an approval in force: the context's ethics approval for a biorepository, any of the collection's approvals for a biobank. A biorepository specimen that names a study or protocol other than its context's is refused (RF004 AC4).
8. **Reading a collection's governance takes authentication only, no collection role (#1346).** `GET /api/collections/:id/governance` answers any authenticated user, as `GET /api/collections` and `GET /api/collections/:id` do (`master-data.routes.js` gates only its writes, with roles 3 and 4). What the read adds is the regime, the context and the approvals, and the approvals carry an authority, a CAAE, a document URI and a checksum: identifiers of an ethics review and of the document recording it, with no participant or personal data. Every role that registers a specimen meets the registration gate (item 7), so it needs to see why a collection refuses one. The writes keep roles 3 and 4. The UI that shows this is the governance panel of the system management collections tab, which only an administrator reaches.

## Why there is no transaction

Three of the four compose stacks run a standalone mongod, where a multi-document transaction fails. The event route updates the collection guarded on the state it read, so two concurrent decisions cannot both land, then appends the event, and restores the collection if the append fails. The outbox's transactional append (#1313) is where this write moves into one transaction.
